# Chessicle 系统设计

规格来源 `docs/PRD.md` + `.ab/prd.json`；技术基线来自客户的 TRD
（`docs/prd-source/chessicle-trd.md`，v0.1 草案）。**TRD 里标 "Proposed" 的都是建议**，
下面每条 `DEC-*` 说明是采纳、改写还是拒绝，以及为什么。

契约在 `_contracts/api-routes.json`（26 条端点 / 7 个域），组件与 NFR 落点在
`.ab/arch.json`，决策索引在 `.ab/design.json`。**「为什么这么选」只在这一份里。**

---

## 威胁模型（`security-hardening` 的五分钟版）

**信任边界**：① 浏览器 → API（全部 26 条端点）；② 照片上传（二进制 + EXIF）；
③ 五个外部数据源的响应（uschess / FIDE / Lichess / Chess.com / 搜索 API）；
④ OCR 与 LLM 两个模型的**输出**；⑤ 家长邮箱里的签名链接。

**资产**：登录验证码与会话、儿童姓名与出生年、家长邮箱、同意记录、上传的照片。

按 STRIDE 扫一遍，落到设计里的有六条：

| 边界 | 威胁 | 落点 |
|---|---|---|
| ① | 假冒：验证码可被枚举 / 无限重发当邮件炮 | `DEC-017` 双维度限流 · `CON-006` |
| ② | 篡改 + 拒绝服务：超大图 / 非图片 / EXIF 带位置 | 上传前压到 ≤1.5MB、服务端剥 EXIF、`Q-005` 的非记谱纸路径 |
| ③ | 泄露 + 拒绝服务：第三方返回任意内容、限速封禁 | `DEC-011` 退避 + 降级 · `CON-009` 礼貌抓取 |
| ④ | **模型输出当敌意**：OCR 吐出的 SAN、LLM 吐出的解释与 URL | SAN 一律过 chess.js 合法性校验；LLM 产出的 URL 一律过 `DEC-010` 白名单 |
| ⑤ | 提权：撤回链接被猜到 → 任意删号 | 签名令牌（HMAC + 用户绑定），`POST /api/consent/revoke` 只认它 |
| 全部 | 泄露：儿童 PII 落日志 | `DEC-016` 列级加密；日志禁打 `parent_email` / `child_name` / 验证码 |

**滥用用例**（进 `agb-qa` 的先写测试）：用别人的 `userId` 调 `/api/consent/request`
换掉家长邮箱；同一邮箱一小时刷 100 个码；上传一张 200MB 的图；让 LLM 在解释里
塞一个白名单外的链接；拿过期的撤回令牌删别人的号。

> **`auth-coverage` 与 `rate-limit-declared` 这一步不跑**（要后端适配器，编码期才跑）。
> 也就是说契约里的 `auth` / `rateLimit` 两栏**现在没有门禁兜底** —— 写错要等到
> 编码期才有人说，而那时端点已经实现完了。26 条里 7 条 `public`（登录发码/验码 +
> 同意的五条），其余 19 条全 `required`；7 条匿名写端点全部 `rateLimit: "required"`，
> 其余一律显式 `"none"`。

## DEC-001 会话用服务端 session cookie，不用 JWT

**选了**：不透明 session id 放 httpOnly + Secure + SameSite=Lax cookie，服务端
`sessions` 表持久化，30 天滑动过期（`Q-017`）。

**为什么**：`EH006` 与 `Q-011` 都要求「立刻销号」——家长拒绝或撤回同意时账号与数据
必须马上失效。JWT 在过期前无法撤销，要撤销就得再加一张黑名单表，那时它相当于
session 表却多了一层签名。**这个产品的核心合规动作是「即时撤销」，而 JWT 恰好
不擅长这件事。**

**被拒的替代**：JWT + refresh（撤销要另建黑名单，反而更复杂）；网关统一鉴权
（v1 只有一个后端服务，多一层运维）。

## DEC-002 登录凭证是一次性邮箱验证码，不设密码

**选了**：`POST /api/auth/request-code` → `POST /api/auth/verify-code`，6 位码、
2 分钟过期、一次性。裁决见 `Q-030`。

**为什么**：家长同意流程本来就是「发码 + 验码」，登录复用同一套机制，代码与运维面
少一半。目标用户是 800–2000 分的学生棋手，让孩子记密码是真实的掉队来源。

**被拒的替代**：邮箱 + 密码（要口令策略、哈希、找回流程，而 `Q-030` 已明确作废
NFR 里那条 password policy）；两者都支持（v1 就要两套鉴权路径，安全面最大）。

## DEC-003 年龄门按出生年判定，<13 才走家长同意

**选了**：注册必填出生年（**只存年份，不存完整生日**）。`<13` → `pending_consent`
走 `WF-01`；`≥13` → `active` 直接可用。裁决见 `Q-031`。

**为什么**：PRD 说「For child users 要家长邮箱」却从没说怎么判定 child ——
这是原文的一处静默缺口。COPPA 管的是 13 岁以下；目标人群里 13–17 是大多数，
把他们也拖进同意流会撞上 PRD 自己写的风险「孩子注册时家长不在旁边」。

**被拒的替代**：<18 全走同意（掉队面最大）；只让用户勾选「我不满 13 岁」
（不存年龄，PII 面最小，但纯自报，`Q-012` 法务复核时大概率不足）。
**存出生年这件事本身增加了一项儿童 PII**，所以它按 `DEC-016` 列级加密。

## DEC-004 家长撤回同意走邮件签名链接，不建家长账号

**选了**：同意邮件里附一个 HMAC 签名、与用户绑定的长期链接 → `PAGE-011`
`/consent/revoke`，点击后走与 `EH006` 同一条硬删流程。裁决见 `Q-011`。

**为什么**：撤回的主体是**家长**，而家长在这个系统里没有账号 —— 建家长身份就要
再来一套注册、登录、鉴权。签名链接把「证明你是那个家长」这件事压缩成一个令牌。

**被拒的替代**：家长后台页面（v1 多一套身份与一个页面）；v1 不做撤回
（`Q-012` 复核结论可能是必须有，届时要返工数据模型）。

## DEC-005 错误全站一种形状：HTTP 状态 + `{ code, message }`

**选了**：所有端点错误一律 HTTP 状态码 + `{ code: string; message: string }`。
`code` 是稳定枚举，`message` 面向用户可读但**不含堆栈、不含内部表字段**。

**为什么**：调用方要能预测。这一版有 SSE 流，流内的失败也用同一形状
（`failure: { code, message }`），否则前端要写两套错误处理。

**被拒的替代**：Problem Details（RFC 9457，字段更多但前端要多解析一层）；
每端点自便（调用方无法预测，正是该记一条 DEC 的切面）。

## DEC-006 创建类 POST 用客户端生成的幂等键，不用自然键

**选了**：`POST /api/games/photo`、`POST /api/games/{gameId}/analysis`、
`POST /api/analysis/{analysisId}/retry` 三条都在 `requestSchema` 里收
`idempotencyKey`（客户端一次生成、重试复用）。同键重发 → 同一个 id；
同键不同请求体 → 409；in-flight → 返回同一个 id 而不是新建。裁决见 `Q-033`。

**为什么**：`Q-013` 定了 120 秒硬上限，比赛场 4G 下客户端一定会重发；而一次
重发意味着重跑一遍 OCR 与 LLM —— 那是真金白银。自然键在这里不成立：同一个人
可以合法地上传两张一模一样的记谱纸照片（两盘棋记在同一格式上）。

**被拒的替代**：不允许重试（比赛场网络下用户体验最差且成本最高）；
自然业务键（如上，会把合法的第二次上传误判成重复）。

> **键是契约，兑现是实现。** 原子占位、同键不同体失败、in-flight 的响应
> 属于 `agb-code`；这一步只把「哪些能重试、键从哪来、冲突长什么样」写进契约。

## DEC-007 列表分页用 cursor，不用 offset

**选了**：`GET /api/games` 收 `{ cursor?, limit? }`，返回 `nextCursor: string | null`。

**为什么**：对局列表按时间倒序，而用户会一边翻页一边上传新对局 —— offset 在这种
写入并发下会漏条和重条。

**被拒的替代**：offset/total（能显示总页数，但会漏条）；不分页（一个赛季就能
超过一屏，`stage-arch` 明确要求现在就写进 schema）。

## DEC-008 进度用 SSE 单向流，不用 WebSocket；断线不续跑

**选了**：两条 `/events` 端点是 SSE。断线即放弃该 job（`EH004`），客户端回来时
用 `GET /api/games/jobs/{jobId}` 读到 `abandoned` 并提示重新上传。

**为什么**：进度是**单向**的，服务端推、客户端不发消息，SSE 够用且比 WebSocket
少一层运维。「断线不续跑」不是偷懒 —— PRD 的 Out of Scope 明确写了不做后台上传
与断点续传，而 `F007` 整条功能的前提就是用户守在页面上。

**被拒的替代**：WebSocket（双向能力用不上）；轮询（20–30 秒的流程里轮询要么
太密要么进度不准）；断线续跑（PRD 明确 out of scope）。

## DEC-009 Stockfish 跑服务端，不跑浏览器 WASM

**选了**：Stockfish 18 服务端 worker 池，版本**钉死**并写进每份报告的
`engineVersion` / `depth`（`CON-008`）。采纳 TRD §4.2 的建议。

**为什么**：学校 Chromebook 是明确的目标设备，浏览器 WASM 引擎在那类机器上又慢
又耗电；而着法分类要可复现（同一局两次分析必须给同一个结论），设备异构做不到这点。

**被拒的替代**：浏览器 WASM（免服务器算力，但分类质量随设备漂移，且在比赛现场
掏空手机电量）。

## DEC-010 外链只走白名单，宁可空推荐也不回退开放网络结果

**选了**：`study_recommendations.url` 写入前过三道：域名 ∈ 白名单
（lichess.org/study · chess.com lessons/articles · youtube.com · chessable.com）；
`youtube.com` 额外查频道白名单（**不是整个 YouTube**）；只许 `https`。
全部不中就丢弃该条。白名单存成配置，加一家不用发版。裁决见 `Q-032`。

**为什么**：这些链接**直接展示给儿童**，而它们由 LLM 从网页搜索结果里挑出来 ——
也就是模型输出当敌意的那条边界（威胁模型 ④）。TRD §4.3 自己标了这条安全注。
**「推荐列表为空」是可接受的降级，「给孩子一个未审链接」不是。**

**被拒的替代**：只允许 lichess + chess.com（最窄，但 PRD 的 F004 明写了
"Youtube videos"，排掉它算缩范围）；开启 safe-search 后放开开放网络
（safe-search 不是白名单，TRD 自己就写着 never raw open-web results）。

## DEC-011 外部源统一退避重试 + 单源失败降级为部分结果

**选了**：所有外部调用走同一个客户端：最多 3 次指数退避，只重试幂等 GET 与
5xx/429。对手检索单源失败时**降级为部分结果并在响应里标明哪个源没到**
（`sourcesQueried[].ok`）。SSE 断线由客户端自动重连并拉一次当前进度。裁决见 `Q-018`。

**为什么**：外部依赖有五个，没有统一策略时每个域会各写一套退避 —— 那是接缝爆炸的
经典形状。把「哪个源没到」放进响应，是因为对手准备报告本来就可能只覆盖一部分来源，
而**沉默的缺失会被用户当成「这个人没有公开棋局」**。

**被拒的替代**：只保 `EH003` 那一条分析重试（爬虫类源抱怨率会很高）；
整体失败（一个 ChessBase 超时就毁掉整份报告）。

## DEC-012 对手身份先解析再找棋局，评分匹配含历史评分

**选了**：先查官方评分源（uschess MSA 爬虫 + FIDE 月度 XML dump）解析出人，
再去 Lichess / Chess.com 找棋局。评分匹配命中条件是**等于当前评分或历史里任一个
评分**。姓名必填、评分与联合会选填（`Q-001`）。全不中报 `no_information`，不猜。
采纳 TRD §4.4 的顺序与 `RatedPlayer` 适配器形状。

**为什么**：PRD 明确要求「只知道旧评分也要能认出人」，这条规则只有评分源的
**历史**能满足；先解析身份再找棋局也避免了拿一个同名账号的棋局做准备。

**被拒的替代**：直接按姓名搜棋局平台（同名会串人，PRD 点名禁止）；
实时爬 FIDE（有月度 dump 就不该实时爬，`CON-009`）。

## DEC-013 浏览器直连契约，不建 BFF

**选了**：SPA 直接调 `_contracts/api-routes.json` 里的 26 条端点。

**为什么**：v1 是单后端服务，页面与端点基本一对一，聚合需求只有分析报告一处
（`GET /api/analysis/{analysisId}` 已经把 moves + summary + recommendations 一起返回）。
加 BFF 等于多写一层端点，而 `contract-coverage` 会要求那一层也被覆盖。

**被拒的替代**：BFF 聚合（v1 没有多后端要聚合）。

## DEC-014 服务端状态用共享 query cache，不用全局 store

**选了**：列表与详情走共享 query cache（按 key 失效），不引全局状态库。
客户端会话不进 JS 可读的 storage —— 会话在 httpOnly cookie 里（`DEC-001`）。

**为什么**：这个应用几乎没有跨页共享的**客户端**状态；它有的是服务端状态的缓存
需求（对局列表、报告、对手报告）。用全局 store 装服务端数据会让每个域各写一套
失效逻辑，集成时才炸。

**被拒的替代**：每页自 fetch（对局列表在 Dashboard 与分析流之间来回，会重复请求）；
全局 store（如上）。

## DEC-015 写操作等响应再改 UI，不做乐观更新

**选了**：着法确认与评分提交都等服务端响应再改界面。

**为什么**：着法确认的下一步直接触发分析（花钱、耗时），乐观更新一旦回滚，用户
会看到「我确认过的着法又变回去了」——而这正是 OCR 纠正流程最不能出现的体验。

**被拒的替代**：乐观更新 + 回滚（这两个操作都不是高频交互，省下的那几百毫秒
换不来回滚的困惑）。

## DEC-016 儿童 PII 列级加密，审计日志只记同意与删除事件

**选了**：全库静态加密之外，`users.child_name` / `users.birth_year` /
`parent_consents.parent_email` 列级加密。验证码只存哈希（采纳 TRD §5）。
`audit_events` 只记同意发出/确认/拒绝、账号删除、照片删除，**且不含任何儿童数据**。
裁决见 `Q-017`。

**为什么**：这三列是 COPPA 语境下的敌意目标，而列级加密让一次库导出泄露不等于
一次儿童身份泄露。审计只记这几类事件是因为它们是**合规上要举证的动作**；
把所有读写都记下来会让审计表本身变成一份儿童行为日志。

**被拒的替代**：只做全库加密（导出即泄露）；全量审计（审计表变成 PII 副本）。

## DEC-017 匿名写端点按邮箱与 IP 双维度限流

**选了**：发码类 5 次/小时/邮箱，验证类 10 次/小时/邮箱，两类各再按 IP 限一道。
裁决见 `Q-034`，采纳 TRD §4.5.2 的 5 次并补上 IP 维度。

**为什么**：只按邮箱限拦不住换邮箱刷（每次刷都发一封真邮件）；只按 IP 限会误伤
**学校 NAT 出口**，而学校 Chromebook 正是明确的目标设备 —— 一个教室共用一个出口 IP。
两维度都要，阈值分开。

**被拒的替代**：只按邮箱（如上）；只按 IP（误伤整个教室）；网关层统一限流
（v1 没有网关，且 gate 看不见那一层）。

## 数据层

schema 在 `_contracts/schema.prisma`（Prisma + PostgreSQL，`Q-026`）。
表名与 `.ab/arch.json` 的 `owns.tables`、`.ab/design.json` 的 `DEC.tables` 一致。

**演进只走 migration，禁止 `db push` / autosync** —— 那是 `stack-conventions/data-layer`
的硬规则，不在这里复述。

TRD §5 的 "Deliberately not stored" 三条原样采纳：分析完成后的记谱照片、
明文验证码、任何用于训练的照片衍生数据。前两条落成 `CON-004` 与 `CON-005`。
