# DESIGN: Team Tasks

对应 `_contracts/api-routes.json` 与 `.ab/design.json`。域：`task`（任务）、
`member`（成员）。表：`tasks`（id, title, description, assigneeId 可空,
status）、`members`（id, name 唯一）。

## DEC-001 不做登录与鉴权，全部端点公开；「当前成员」只是本地会话的显示状态

**选了**：所有 `/api/*` 端点 `auth: public`，不做任何身份校验。PAGE-001 的
「当前成员」下拉（IC-01）只写本地会话状态，用于给自己的任务卡片加高亮，
不作为请求参数发送给后端，也不构成权限判断的依据。

**为什么**：PRD §9.1 已经把这条列为默认决策——本轮是 Tier S 演示，
引入鉴权会把项目推到 Tier M，与「不自行扩展范围」的约束冲突。同时 §2.2
状态机里每条转移的执行者都写的是「任意成员」，也就是说就算做了鉴权，
业务规则也不需要按用户做区分。

**被拒的替代**：给 `/api/*` 加会话鉴权（如 JWT/cookie session）——
需要登录页、密码/邀请流程，这些都不在本轮范围内，且没有 PRD 依据。

## DEC-002 任务状态转移走独立端点，服务端按 WF-01 校验合法转移，不接受客户端直接写任意 status

**选了**：`POST /api/tasks/:taskId/transitions`，请求体 `{ to: string }`，
服务端读取任务当前 status，只在 WF-01 定义的转移表（`todo→in_progress`、
`in_progress→todo`、`in_progress→done`）里查表放行，其余一律拒绝。

**为什么**：PRD §2.1 明确把「done → in_progress」（重新打开已完成任务）
列为非目标，理由是 `done` 被定为终态、允许回流会使状态机无终态。如果把
status 作为 `PATCH /api/tasks/:taskId` 的普通字段暴露给客户端，
状态机的合法性就完全依赖前端不发错请求，后端挡不住一次越权或有 bug 的
客户端请求把已完成任务拖回进行中。独立端点把这条约束放在服务端，
`PATCH` 端点因此不再包含 `status` 字段。

**被拒的替代**：把 `status` 并入 `PATCH /api/tasks/:taskId` 的可写字段——
状态机校验要么被绕过、要么和标题/描述/负责人的保存逻辑耦合在一起，
职责不清。

## DEC-003 共享数据落在服务端持久化存储，而不是仅存于客户端本地

**选了**：所有任务与成员数据经由后端 API 读写，落地到服务端可持久化的
存储（具体介质留给详设/技术方案阶段，本决策只锁定「必须经过服务端、
必须持久化」这两条）。

**为什么**：AC-14 要求「成员 A 在设备 1 创建任务后，成员 B 在设备 2
刷新 `/` 即可看到该任务」，这只能靠一份所有设备都能读到的共享数据源
满足；仅存在单个浏览器的 `localStorage` 做不到跨设备可见。同时看板
默认只显示当前工作（VAR-01），刷新页面必须能看到别人写入的数据，
说明状态不能只活在某一次前端会话里。

**被拒的替代**：客户端本地存储（`localStorage`/`IndexedDB`）——
直接违反 AC-14，数据无法跨设备/跨会话共享；服务端进程内内存、不落盘——
在单实例部署下短期可用，但把「需要持久化」这条约束悄悄转嫁给了部署
拓扑（一旦重启或多实例就丢数据/数据不一致），不作为本决策的选项。

## DEC-004 移除成员时，其名下任务在同一次请求内改为「未分配」，不做前置阻断

**选了**：`DELETE /api/members/:memberId` 在同一次请求里完成两件事：
删除该成员记录，并把 `assigneeId` 等于该成员的所有任务的 `assigneeId`
置为 `null`。IC-20 不需要先检查该成员是否有在办任务再决定是否允许删除。

**为什么**：PRD §9.3 的默认决策是「任务保留，负责人置为未分配」，
依据是任务是团队资产，成员离开不应带走工作记录；对应 AC-13
（移除后任务仍存在、负责人显示未分配）。把这两步放在同一次请求里
而不是要求前端先改派完所有任务再允许删除，是因为 PRD 没有把
「移除前必须先改派完毕」列为本轮行为（那是 §9.3 明确写出的兜底方案，
只在人工裁决改变默认决策时才启用）。

**被拒的替代**：删除前要求该成员名下当前工作数为 0，否则禁用 IC-20 并
提示原因——这是 §9.3 兜底方案里描述的另一套行为，只有在默认决策被
人工推翻时才应该实现，本轮不采用。

## DEC-005 技术栈：React+Vite+TypeScript 前端，Node.js+Express+TypeScript 后端，SQLite 持久化，Vitest+Supertest 测试

**选了**：

- **前端**（目录 `client/`）：React 18 + Vite + TypeScript 单页应用，
  用 React Router 实现 PRD §3 的四个路由（`/`、`/tasks/new`、
  `/tasks/:taskId`、`/members`）。服务端状态（任务列表、成员名册）用
  React Query 做请求缓存与失效，不引入额外的全局状态管理库；
  「当前成员」这类纯本地会话状态（IC-01）用组件内 state 即可。
- **后端**（目录 `server/`）：Node.js + Express + TypeScript，直接实现
  `_contracts/api-routes.json` 里的 8 个端点，不引入额外的应用框架层。
- **数据层**：SQLite 单文件数据库，经 `better-sqlite3`（同步、进程内、
  无需单独启动数据库服务）读写，映射到本文件顶部已定义的 `tasks` 与
  `members` 两张表。
- **测试**：Vitest 做前端组件与后端纯逻辑（尤其是 DEC-002 的 WF-01
  转移校验表）的单元测试；Supertest 对 Express 路由做集成测试，
  直接命中一个每次测试运行时新建的临时 SQLite 文件。

**为什么**：README 与本文件顶部（现已移除的重入待决项）明确要求 Arch
Agent 在这一阶段把技术栈钉死为正式 `DEC-*`，不能留到 detail/code 阶段
含糊决定。选择依据是 Tier S 的两个硬约束——规模小、且要求「本地可
验证性」（不依赖额外起容器或云账号就能跑通全部 AC）：

- React + Vite 对 PRD 里「单页应用」「键盘可达、焦点可见」（§8）这类
  零散 UI 需求摩擦最小，不需要 SSR/RSC 之类当前不需要的能力。
- Express 是端点数量少（8 条）、无鉴权（DEC-001）、无复杂中间件链场景
  下最小依赖的选择。
- SQLite 满足 DEC-003「必须经过服务端、必须持久化」这条约束的同时，
  是单文件、进程内嵌入的，不需要额外的数据库服务器或云托管账号，
  与 Tier S「本地可验证」的前提直接对应；`better-sqlite3` 的同步 API
  和内置事务也天然规避「移除成员同时批量置空 assigneeId」（DEC-004）
  这种操作里的读-改-写竞争。
- Vitest 复用 Vite 已有的构建管线，前后端共用一套测试运行器配置；
  Supertest 是 Express 生态测试真实路由处理器（而不是起真实网络端口）
  的标准方式，两者都不引入额外的运行时基础设施。

**被拒的替代**：

- 前端用 Next.js——本产品没有 SEO 或服务端渲染诉求，PRD 未提出多页面
  路由之外的需求，引入文件路由/RSC 概念对 Tier S 是不必要的复杂度。
- 后端用 Nest.js——装饰器、依赖注入容器等框架开销，对 8 个公开端点、
  无分层业务规则的场景是过度设计。
- 数据层用 Postgres/MySQL（本地容器或云托管）——需要额外起数据库服务
  或云账号才能验证，与「本地可验证性」冲突，且 PRD §8 的规模上限
  （看板 200 条任务）远低于需要关系型数据库集群能力的门槛。
- 数据层用纯 JSON 文件读写——没有事务保护，两名成员同时写入容易出现
  读-改-写竞争导致互相覆盖，与 AC-14 的多设备并发写入场景冲突。
- 测试用 Jest——能力与 Vitest 等价，但需要额外配置才能对齐 Vite 的
  ESM 构建环境，配置摩擦更高。
