# Agent 评测协议

> 本文为 `AGENT-EVALUATION-PROTOCOL.md` 的中文译本。配置字段名、状态值和标识符保持英文，便于与实现对照。

**版本：** 0.3  
**状态：** 草案  
**目的：** 一份简短、与具体实现无关的规范，用于评测完整的 agent 工作流，并为每一步选择合适的模型、供应商、提示词和工作流配置。

## 1. 本协议用来做什么

一条 agent 工作流通常包含多种不同工作：理解请求、规划、检索信息、使用工具、生成产物、检查结果、从错误中恢复。某一步最好的模型，不一定也是另一步最好的模型。

本协议提供一种可重复的方法，用来回答四个问题：

1. 工作流是否正确、安全地完成了任务？
2. 每一步用哪种模型和配置效果最好？
3. 在可接受的选项中，哪家供应商的成本和完成时间最好？
4. 另一个人能否根据留下的证据复现该结果？

它不产出一份通用的模型排行榜。每一条推荐都只适用于：已定义的工作流步骤、测试集、运行模式，以及评测版本。

## 2. 核心原则

### 质量必须先过门

候选方案必须先满足规定的正确性、安全、可靠性和策略条件。更快或更便宜，不能用来抵消未满足的必要条件。

### 重要指标必须分开报告

不要把单一加权分数当作官方结果。至少报告：

- 任务成功；
- 必要检查通过率；
- 可靠性；
- 经评判的质量；
- 工作流步数和重试次数；
- 缓存使用情况；
- 每个成功任务的成本；以及
- 完成时间，样本足够大时包括第 50 和第 95 百分位。

### 评测工作流，而不只评最终答案

记录决策、工具调用、中间产物、重试、检查点（checkpoint）和最终输出。看起来合理的最终答案，可能掩盖低效或不安全的过程。

### 主观质量优先用比较证据

当质量无法完全用确定性规则检查时，直接比较输出，并对明确定义的维度打分。在依赖自动化评判器之前，先用专家人工判断对其进行校准。

### 让不确定性可见

样本小或不一致时，应给出方向性结论，而不是虚假的精确数字。报告必须区分：失败、评测器错误，以及「未评测」。

## 3. 运行前必须定义什么

每个工作流步骤都必须有一份带版本的评测规格，其中包含：

| 必填项 | 通俗含义 |
|---|---|
| 任务 | 这一步预期要做什么。 |
| 目标 | 对用户或业务真正重要的结果。 |
| 上下文 | 该步骤可获得的信息、工具、权限，以及前序步骤的输出。 |
| 目标行为 | 优秀的过程和输出看起来是什么样。 |
| 失败模式 | 已知的做错、不安全、不完整、低效或误导的方式。 |
| 测试用例 | 有代表性的常规案例、困难案例、边界案例和已知失败。 |
| 必要检查 | 必须通过的条件，例如 schema 有效性、编译、引用核验、策略合规或字段级准确性。 |
| 评判维度 | 需要经校准的人工或模型判断的质量，例如推理质量、有用性、业务依据或视觉设计。 |
| 运行约束 | 成本上限、完成时间上限、隐私规则，以及允许使用的工具。 |
| 候选方案 | 把模型、供应商、提示词、工具配置和生成参数当作一个可测试选项。 |

任何实质性条目的变更，都会产生一个新的评测版本。

## 4. 配置与可选设置

一次评测由一份带版本、人类可读的配置文件定义。界面可以通过引导式表单生成该文件，但保存下来的配置才是可复现的事实来源。

用户可以选择或定义以下内容：

| 配置区域 | 可选设置 |
|---|---|
| 工作流范围 | 工作流、包含的步骤、步骤顺序，以及简单的端到端对照。 |
| 测试数据 | 测试集版本、包含的用例、抽样规则、数据划分，以及受保护的 holdout 用例。holdout 用例留给最终验证，而不是日常调参。 |
| 候选方案 | 模型、推理供应商、系统提示词、生成参数、推理设置、上下文限制、工具，以及该候选可执行的工作流步骤。 |
| 试验计划 | 每个用例的重复次数、支持时的随机种子、并行运行上限、总花费上限，以及停止规则。 |
| 评测方法 | 必要检查、直接比较、维度评分细则、基于问题的检查、自动化评判器，以及人工评审。 |
| 资格门槛 | 必要检查阈值、最低可靠性、取消资格的失败模式，以及适用时的最长完成时间。 |
| 运行模式 | 在合格候选中选成本最低、在成本上限内选最快，或在成本和时间上限内选最高保障。 |
| 缓存测试 | 冷缓存、热缓存或两者都测；缓存命名空间；以及热缓存测试所用的、贴近生产的请求序列。 |
| 长时运行行为 | 最长运行时间、检查点触发条件、恢复策略、允许的替换模型，以及最大恢复尝试次数。 |
| 数据处理 | 执行位置、允许的端点、脱敏策略、保留期限，以及面向客户的报告可以披露什么。 |
| 报告 | 内部证据视图、客户视图、审计视图、对比运行，以及不确定性要求。 |

### 最小配置示例

下面使用 YAML（一种人类可读的配置格式）。这只是示例；实现也可以接受等价的结构化格式。

```yaml
protocol_version: "0.2"
run_name: "product-requirements-and-code-handoff"
budget_usd: 100

workflow:
  control_candidate: "single-model-control"
  steps:
    - id: "requirements"
      task_file: "tasks/requirements.md"
      test_set: "test-data/requirements-v3"
      candidate_ids: ["candidate-north", "candidate-east"]
      required_checks: ["evidence-trace", "scope-consistency"]
      judged_dimensions: ["business-grounding", "causal-strength", "usability"]
      operating_mode: "highest-assurance"

    - id: "code-handoff"
      task_file: "tasks/code-handoff.md"
      test_set: "test-data/code-handoff-v2"
      candidate_ids: ["candidate-east", "candidate-west"]
      required_checks: ["compilation", "automated-tests", "security-policy"]
      maximum_completion_time_seconds: 120
      operating_mode: "lowest-cost-within-time-limit"

candidates:
  - id: "candidate-north"
    model: "provider/model-name"
    provider_route: "primary-route"
    prompt_file: "prompts/north.md"
    generation_settings:
      temperature: 0.2

execution:
  trials_per_case: 3
  cache_mode: "both"
  resume: true
  checkpoint_after_each_step: true

reporting:
  views: ["internal", "client"]
  redact_raw_client_data: true
```

`budget_usd` 中的货币单位是美元。其中的标识符是用户定义的稳定名称；它们不会向评判器暴露供应商名称。

## 5. 合同

合同使运行器、工作流、模型、评测器和报告可以各自独立变更。

### 候选适配器合同

每个模型或供应商适配器接受一份规范化请求，其中包含：

- 任务和步骤标识符；
- 输入和允许的上下文；
- 可用工具和权限；
- 前序步骤输出；
- 生成参数；以及
- 可选的、用于恢复的检查点。

它返回：

- 响应内容和生成的产物；
- 完成状态：成功、拒绝、超时、格式错误的输出、取消，或供应商错误；
- 可用时的 token 及供应商报告的用量；
- 开始时间、首次响应时间和完成时间；
- 可用时的缓存信息；
- 模型和供应商路由标识符；
- 支持时的可恢复检查点；以及
- 不含密钥的结构化错误详情。

供应商特有字段可以作为元数据保留，但必需的规范化字段必须保持可移植。

### 评测器合同

每个评测器接受步骤规格、测试用例、候选输出和相关轨迹。比较型评测器还会收到另一份已匿名的输出。

它返回：

- 结果状态：通过、失败、未评测，或评测器错误；
- 该方法支持时的数值分数；
- 适用时的比较结果：第一份输出、第二份输出，或平局；
- 来自输出或轨迹的引用证据；
- 解释和置信度；
- 评测器名称和版本；以及
- 是否需要人工评审。

评测器错误绝不能被转换成候选方案的失败。

### 检查点合同

检查点包含：已完成工作、当前计划、剩余工作、产物、证据来源、工具状态、假设、未解决问题、预算使用、已用时间、隐私标签，以及格式版本。另一个兼容模型必须能在恢复前验证该检查点。

### 必要检查合同

确定性必要检查接收步骤规格、测试用例、输出产物，以及允许的轨迹字段。它返回通过、失败、未评测或评测器错误；可选的连续型度量；证据；以及其实现版本。

## 6. 评测方法

用能够可靠测量该属性的、尽可能小的方法组合。

### 确定性检查

对答案明确的属性使用可执行检查。例如：有效的结构化输出、编译、测试完成、精确字段抽取、引用解析、文件完整性，以及策略规则。

必要检查充当资格门槛。其结果为：通过、失败、评测器错误，或未评测。

### 直接比较

对于主观差异，展示同一测试用例的两份匿名输出，询问哪一份更满足既定标准。交换它们的展示顺序以检测位置偏差。差异无意义时允许平局。

### 基于评分细则的打分

在带行为锚点的连续量表上，对明确定义的维度打分。不要索取无法解释的总分。例如，业务依据可以衡量：有多少实质性建议得到所提供证据的支持，以及与预期业务结果之间因果联系的强度。

### 基于问题的检查

把需求变成可回答的问题，例如「每个提议的功能是否都对应一个已陈述的用户问题？」记录答案、支持证据和置信度。

### 人工评审

对高风险决策、新颖失败模式，以及由品味主导的输出，使用专家评审。人工评审也是校准自动化评判器的参照。

## 7. 执行生命周期

1. **校验配置。** 确认引用的步骤、候选、测试集、检查、凭证、限额和报告权限都存在。拒绝矛盾或不安全的设置。
2. **预览运行。** 在执行前展示计划中的生成次数、评判次数、必要检查次数、预估花费区间，以及预期数据去向。
3. **冻结运行。** 写入不可变的运行清单，包含工作流、提示词、模型、供应商、工具、数据、评测器、阈值和基础设施版本。
4. **运行对照。** 测试简单基线；在考虑切换模型时，包括用一个强模型跑完整工作流的对照。
5. **生成重复试验。** 让每个候选在相同测试用例上运行。超时、拒绝、格式错误的响应、取消和失败尝试都作为结果保留。
6. **检查点与恢复。** 每完成一个单元就保存结果。在启用恢复的情况下重新启动时，必须跳过已在相同内容哈希下完成的工作。
7. **捕获轨迹。** 存储步骤输入输出、工具调用、重试、检查点、token 用量、缓存状态、成本和时间。
8. **应用必要检查。** 淘汰未达到规定资格阈值的候选。
9. **评判合格输出。** 按情况使用直接比较、维度分数、基于问题的检查或人工评审。
10. **估计不确定性。** 重复足够的用例和试验以显示变异。报告置信区间，或给出明确的方向性警告。
11. **按运行模式选择。** 在合格候选中，应用已声明的优先级：最低成本、在成本上限下最低完成时间，或最高保障。
12. **端到端比较。** 确认提议的模型组合，在计入交接、缓存和路由开销后，优于简单对照。
13. **渲染已批准的视图。** 按报告策略产出机器可读证据，以及内部、客户或审计视图。

只有传输失败可以自动重试，且不计入一次已完成的候选尝试。其他失败仍是被测量结果的一部分。达到花费或时间上限时，运行干净地停止，并记录未完成的工作，而不是悄悄丢弃。

## 8. 为不同步骤选择不同模型

当步骤需要明显不同的能力或经济性时，切换模型可能有帮助。只有在端到端证据支持时，才应采用。

使用三个独立阶段：

1. **评测：** 用相同的测试用例和重复次数，在每个适用的工作流步骤上运行每一种配置。一种配置是：一个模型、一条供应商路由、一份提示词、一套工具设置，以及一组生成参数。不要基于假设预先把配置指派给步骤。
2. **选择：** 用步骤级证据为每一步提议一种配置。结果可能是一种配置处理所有步骤，也可能是不同配置处理不同步骤。
3. **验证：** 从头到尾运行提议的组合工作流。把它与每种单一配置工作流，以及当前生产工作流进行比较。

例如，如果配置 A、B、C 都能执行理解、规划、执行和验证这四步，则评测阶段包含十二个测试单元：三种配置乘以四个步骤。只有在这些测试之后，提议的工作流才可能选择 A 做理解、B 做规划、C 做执行、A 做验证。

对模型之间的每一次交接，定义：

- 允许的输入和输出字段；
- 事实与检索证据的来源；
- 不确定性和未解决问题；
- 大小限制和压缩规则；
- 隐私分级；以及
- 中断的步骤如何恢复。

测量切换引入的额外成本、完成时间、转译损失、缓存中断和运维复杂度。如果改进没有意义或无法重复，则保留单模型对照。

## 9. 非确定性与多模态工作

产品需求撰写、情境问答、界面设计、图像生成和视频生成这类任务，需要分层评测。

使用此顺序：

1. 产物有效性与安全；
2. 必要内容与事实符合度；
3. 任务特定一致性，例如角色身份或帧间连续性；
4. 技术质量；
5. 经校准的质量或品味判断；以及
6. 成本与完成时间。

对于视频，在指定时间范围内评测提示词符合度，而不是只在整段视频层面评测。只比较已通过有效性和安全检查的输出。对整体设计质量使用多名盲评评审者，记录分歧，并且不要把审美偏好呈现为客观真理。

## 10. 长时任务与检查点

长时任务必须有命名检查点。每个检查点存储：

- 已完成工作和已生成产物；
- 当前计划和剩余工作；
- 工具状态和外部引用；
- 决策、假设和未解决问题；
- 预算和已用时间；以及
- 另一个兼容模型可以据此恢复的带版本格式。

测试内容不只是最终完成。在计划好的点中断试验，用相同模型和不同模型分别恢复，并测量恢复成功、重复工作、信息丢失，以及增加的成本和时间。

## 11. 客户托管评测

评测运行器应能在客户控制的公有云或私有云环境中执行。客户提供：

- 可调用的工作流或打包好的运行器；
- 已批准用于评测的代表性数据；
- 预期行为、已知失败模式，以及领域评审人；
- 通过客户密钥管理器提供的凭证；以及
- 规定哪些证据可以离开该环境的规则。

原始客户数据默认应留在客户环境中。只导出已批准的报告视图，例如聚合指标、脱敏示例、决策轨迹和未解决风险。把内部评测器诊断和原始轨迹放在更受限的视图中。

可重复性要求：钉死版本、内容哈希、固定的测试集标识符、记录的基础设施和供应商设置，以及不可变的运行清单。

## 12. 输出合同

每次运行产出一个带版本的运行目录，或等价的对象存储前缀，其中包含：

1. 一份描述究竟测了什么的清单；
2. 原始和规范化的试验记录；
3. 检查点和恢复记录；
4. 带证据的必要检查和评判记录；
5. 按步骤的结果表；
6. 端到端工作流比较；
7. 带决策轨迹的推荐；
8. 不确定性、限制和未解决风险；
9. 与先前运行比较时的变更报告；以及
10. 已批准的人类可读报告视图。

机器可读报告是权威来源。常见表示是 JSON，通常以 `.json` 文件名存储。面向人的报告是从权威记录派生出的受控视图。

### 每次试验的最低记录

每条试验记录包含：运行、工作流、步骤、测试用例、候选和试验标识符；时间戳；完成状态；规范化输出引用；轨迹引用；必要检查结果；用量和成本；缓存状态；重试历史；检查点；以及错误。

### 每步结果的最低内容

每个步骤结果包含：资格及原因；任务成功率和必要检查通过率；可靠性；比较判断；连续维度度量；每次尝试和每个成功任务的成本；完成时间分布；工作流步数和重试次数；缓存结果；不确定性；以及每种运行模式下推荐的候选。

### 推荐轨迹

推荐轨迹按顺序列出每一次过滤和比较、每个被剔除的候选及其原因、剩余权衡、所选运行模式、最终选择，以及该结果是确定的、方向性的，还是需要人工评审。

### 报告视图

- **内部证据视图：** 完整轨迹、原始示例、评测器诊断和调试数据。
- **客户视图：** 已批准的聚合指标、脱敏示例、推荐逻辑、限制和风险。
- **审计视图：** 不可变清单、哈希、版本、决策轨迹、审批和策略事件。
- **变更视图：** 两次运行之间在配置、证据、表现和推荐上的差异。

## 13. 最小可用实现

第一个可用版本必须支持：

- 文本、代码和结构化数据的工作流步骤；
- 与模型和供应商无关的适配器；
- 确定性检查和经校准的模型判断；
- 重复试验和不确定性报告；
- 成本、时间、可靠性、工作流步骤、重试和缓存度量；
- 可恢复运行和基于内容的缓存；
- 单模型端到端对照；
- 客户托管执行及脱敏报告导出；以及
- 带版本的清单，以及运行之间的比较。

视频和其他多模态评测器可以通过相同的产物、轨迹和打分合同后续加入。

## 14. 符合性

当一个实现能够做到以下事项时，即符合本协议：

- 读取带版本的步骤规格；
- 保留所有必需的结果状态；
- 在优化成本或速度之前应用资格门槛；
- 分别保留结果指标和运行指标；
- 根据存储的证据复现一条推荐；以及
- 导出机器可读的运行包，且不要求特定模型、供应商、网关或评测框架。

## 15. 本协议有意不决定的事项

本协议不要求某一种评测框架、模型网关、推理供应商、评判模型、存储系统或托管平台。那些是可替换的实现选择。它也不声称某一个模型普遍最好，或主观质量可以被还原成客观真理。
